Phần 1: Khởi nguồn & Bối cảnh

Spaghetti Code vs Kiến trúc phân tầng MVC

Trygve Reenskaug (Xerox PARC 1979) phát minh MVC để giải phóng giao diện người dùng khỏi mớ hỗn độn nguyên khối.

Ví dụ: Ứng dụng Console / Standalone truyền thống

Gộp Scanner, thuật toán tính điểm và System.out.println vào 1 hàm → Không thể viết Unit Test tự động, đập bỏ toàn bộ mã khi chuyển sang Web GUI.

Giải pháp MVC: Phân ranh giới rõ ràng

Tách rời 3 mối quan tâm: Dữ liệu (Model) độc lập 100% với hiển thị (View), điều phối qua Controller → Kiểm thử độc lập, bảo trì dài hạn.

Phần 1: Khởi nguồn & Triết lý

Separation of Concerns (SoC) & Single Responsibility

Chia nhỏ phần mềm thành các lớp chuyên biệt: mỗi thành phần chỉ có một lý do duy nhất để thay đổi.

Separation of Concerns (SoC)

Mỗi thành phần chịu trách nhiệm duy nhất một khía cạnh. Sửa giao diện không làm hỏng công thức tính tiền.

Single Responsibility (SRP)

Mỗi class chỉ có 1 lý do duy nhất để thay đổi. Triệt tiêu tác động lan truyền (Ripple Effect) khi bảo trì.

Loose Coupling, High Cohesion

Liên kết giữa các tầng là tối thiểu, mã nội bộ gắn kết cao → Tiền đề cho Unit Test độc lập hoàn toàn.

Phần 2: Tam giác M - V - C

Thành phần 1: Model — Quản lý dữ liệu & Quy tắc nghiệp vụ

Trái tim của hệ thống: Độc lập tuyệt đối với tầng hiển thị, nắm giữ tính toàn vẹn và các quy tắc bất biến.

Trách nhiệm lõi State & Invariants

• Quản lý dữ liệu thực thể và kiểm soát tính bất biến nghiệp vụ.
• Đóng gói công thức tính toán, trạng thái tài khoản, giỏ hàng.
• Không chứa bất kỳ thẻ HTML hoặc mã UI nào.

Mô hình thực tế Entity & DTO Pattern

• Java Web chuẩn: JavaBeans/DTO (Encapsulation) kết hợp DAO truy xuất qua kết nối CSDL.
• Enterprise hiện đại: Domain Entity kết hợp Repository Pattern (Spring Data JPA / EF Core).

Phần 2: Tam giác M - V - C

Thành phần 2: View — Biểu diễn giao diện thụ động

View nhận dữ liệu đã được Controller chuẩn bị sẵn, kết xuất ra HTML/CSS và không tự ý gọi CSDL.

Passive View Thụ động 100%

• View chỉ vẽ những gì Controller đưa qua Request Scope.
• Không bao giờ chứa logic tính toán tài chính hay câu lệnh SQL.
• Thu nhận tương tác người dùng (Click/Submit) và gửi về Controller.

Quy chuẩn Template Trình diễn Declarative

• Java Web: Dùng JSTL (<c:forEach>) & EL (${item.price}), loại bỏ Scriptlet (<% %>).
• Enterprise: Razor (.cshtml), Thymeleaf (th:each), React JSX.

Phần 2: Tam giác M - V - C

Thành phần 3: Controller — Bộ điều phối & Định tuyến luồng

Trung gian đón nhận HTTP Request, giải mã tham số, kích hoạt Model và điều hướng hiển thị View.

Quy trình 4 bước Vòng điều phối chuẩn

1. Nhận Request: Đón bắt URL Mapping & HTTP Method.
2. Bóc tách Input: Đọc query params/body, validate cơ bản.
3. Gọi Model/Service: Ủy quyền xử lý nghiệp vụ, lấy kết quả.
4. Điều hướng: Nạp data vào Scope và Forward/Redirect tới View.

Công nghệ triển khai Servlet & Action

• HttpServlet (Java Web): request.getParameter() → Gọi DAO → setAttribute() → forward().
• Enterprise: Spring @RestController, ASP.NET Core Controller.

Phần 3: Luồng hoạt động & Sơ đồ

Sơ đồ tương tác 3 chiều: Client - Controller - Model - View

Phân tách tường minh giữa luồng vào (Input Flow) và luồng ra (Output Flow) với các xung photon chuyển động tuần hoàn.

1. Input Flow

Client gửi Request → Controller tiếp nhận, validate và kích hoạt xử lý tại Model.

2. Processing Flow

Model truy vấn CSDL, thực thi quy tắc kinh doanh và đóng gói dữ liệu thành DTO.

3. Output Flow

View nhận DTO, render thành HTML stream hoàn chỉnh và gửi trả về trình duyệt.

Phần 3: Luồng hoạt động & Sơ đồ

Vòng đời HTTP Request-Response trên Web (Model 2)

Pipeline xử lý tuần tự từ lúc nhận gói tin HTTP tại Front Controller đến khi trả về giao diện hoàn tất.

1. Request

Browser gửi yêu cầu HTTP kèm Headers & Parameters.

2. Dispatch

Front Controller phân tích định tuyến và bảo mật.

3. Process

Controller gọi Service/DAO để cập nhật CSDL.

4. Response

View Resolver dựng giao diện và gửi về Client.

Phần 3: Luồng hoạt động & Sơ đồ

Desktop MVC (Active Model) vs Web MVC (Passive Model)

Sự chuyển dịch bản chất từ kiến trúc hướng sự kiện (Observer Pattern) sang mô hình phi trạng thái (Stateless).

Desktop MVC (Active Model)

Stateful Observer

Áp dụng trong Desktop GUI (Java Swing, WPF, Smalltalk):

  • • Observer Pattern: Model chủ động thông báo khi dữ liệu đổi (notifyObservers()).
  • • View tự cập nhật: View lắng nghe Model trực tiếp và tự vẽ lại trong bộ nhớ RAM.
  • • Kết nối liên tục: Trạng thái ứng dụng tồn tại xuyên suốt phiên làm việc.

Modern Web MVC (Passive Model)

Stateless Request-Response

Áp dụng trong hệ thống Web (Servlet/JSP, Spring, ASP.NET):

  • • Giao thức HTTP Stateless: Kết nối đóng ngay khi máy chủ gửi xong Response.
  • • View hoàn toàn thụ động: Controller bắt buộc phải lấy Model và nhồi vào View.
  • • Vòng đời ngắn: Controller và ViewModel được tạo và giải phóng theo từng Request.
Đúc kết kiến trúc quan trọng: Trên môi trường Web, Controller đóng vai trò trung gian tuyệt đối, điều phối dữ liệu từ Model vào View Resolver, thay vì để View tự động lắng nghe Model như thời Desktop.
Phần 4: So sánh kiến trúc & Triển khai

So sánh kiến trúc: MVC vs MVP vs MVVM

Sự tiến hóa của các biến thể phân tầng giao diện người dùng (UI Architectural Patterns).

Tiêu chí MVC MVP MVVM
Cơ chế trung gian Controller (Routing, điều hướng) Presenter (Thao tác qua View Interface) ViewModel (Data Binding hai chiều)
Ràng buộc View - Model View đọc Model hiển thị View và Model không biết nhau View liên kết tự động qua ViewModel
Testability Khá tốt (Test riêng biệt) Rất cao (Mock View Interface) Rất cao (ViewModel độc lập UI)
Phần 4: So sánh kiến trúc & Triển khai

Triển khai MVC trong Enterprise Frameworks

Bố cục 3 tầng ngang chuẩn mực (3-Tier Layered Stack): Đơn hướng, tường minh và tách biệt trách nhiệm.

L1
Presentation Layer (Giao diện & Điều phối) MVC / REST

Nhận HTTP Request, trích xuất tham số, xác thực dữ liệu (Validation), điều hướng và trả về DTO/View.

@RestController ControllerBase
↓ Calls Business Services (DTO In/Out)
L2
Business Service Layer (Quy tắc nghiệp vụ lõi) Domain Logic

Xử lý nghiệp vụ, tính toán chiết khấu/thuế, quản lý giao dịch an toàn (ACID) và kiểm soát toàn vẹn dữ liệu.

@Service @Transactional
↓ Queries & Persists Domain Entities
L3
Data Access Layer (Truy xuất dữ liệu & CSDL) Persistence

Giao tiếp cơ sở dữ liệu qua ORM/Repository, sinh câu truy vấn SQL tối ưu và ánh xạ dữ liệu thành Entity.

@Repository DbContext / JPA
Java · Spring Boot: @Controller → @Service → JpaRepository → MySQL/PostgreSQL
.NET · ASP.NET Core: ControllerBase → BusinessService → DbContext (EF Core) → SQL Server
Phần 5: Anti-Patterns & Best Practices

Anti-Patterns: Cân bằng tải kiến trúc Controller

Cảnh báo lỗi thiết kế vi phạm nguyên tắc SOLID và làm suy giảm nghiêm trọng chất lượng phần mềm.

Fat Controller (God Object)

Gia tăng Cyclomatic Complexity, phát sinh Tight Coupling và triệt tiêu khả năng Unit Testing.

Anemic Domain Model

Model chỉ chứa getter/setter không có hành vi nghiệp vụ, phân tán logic ra ngoài tầng ứng dụng.

View DB Leakage

View gọi truy vấn trực tiếp gây lỗi mất kết nối (LazyInitialization) và sụt giảm hiệu năng nặng nề.

Phần 5: Anti-Patterns & Best Practices

Best Practices: Tối ưu hóa kiến trúc MVC

Các nguyên tắc vàng giúp hệ thống dễ bảo trì, mở rộng an toàn và đạt chuẩn công nghiệp.

Quy tắc 01

Skinny Controller, Fat Model

Controller siêu mỏng: chỉ nhận request → ủy quyền cho Service → trả kết quả. Giữ các quy tắc bất biến trong Rich Domain Model.

Quy tắc 02

Sử dụng DTOs & ViewModels

Không đưa Domain Entity trực tiếp lên View. Sử dụng DTO để che giấu trường nhạy cảm và chống tấn công Over-Posting.

Quy tắc 03

Dependency Injection (DI)

Tiêm phụ thuộc qua Constructor Injection. Không dùng từ khóa new trong Controller để đảm bảo khả năng Mock Test.

Quy tắc 04

Centralized Exception Handling

Không viết try-catch tràn lan trong Controller. Sử dụng bộ bắt lỗi tập trung (Global Exception Middleware / Advice).

Phần 5: Đánh giá & Kết luận

Đánh giá kiến trúc: Ưu điểm & Đánh đổi (ISO/IEC 25010)

Ưu điểm Lợi ích kỹ thuật
  • • Testability cao: Kiểm thử độc lập Model & Controller không cần dựng môi trường UI.
  • • Maintainability: Đổi công nghệ giao diện mà không ảnh hưởng logic lõi.
  • • Team Parallelism: Frontend và Backend lập trình song song qua hợp đồng API/DTO.
Đánh đổi Hạn chế & Chi phí
  • • Initial Overhead: Với CRUD nhỏ, kiến trúc tạo ra nhiều file và lớp trung gian thừa.
  • • Nguy cơ Fat Controller: Cần kỷ luật thiết kế để tránh nhồi nhét logic vào Controller.
  • • Kém linh hoạt với Real-time: Cần nâng cấp lên MVVM hoặc Component-based khi làm SPA lớn.
Phần 5: Đánh giá & Kết luận

Tổng kết & Thông điệp cốt lõi

01

SoC là Chân lý

Tách biệt UI, Business Logic và Điều hướng là nền móng để phần mềm trường tồn.

02

Model là Trái tim

Đầu tư vào Rich Domain Model. View và Controller chỉ là lớp vỏ bọc bên ngoài.

03

Giữ Controller Mỏng

Ủy quyền xử lý cho Service Layer. Controller chỉ làm nhiệm vụ tiếp nhận và điều hướng.

04

Linh hoạt Biến thể

Hiểu rõ khi nào dùng Web MVC, khi nào chuyển sang MVP hoặc MVVM cho phù hợp.

"Kiến trúc tốt không phải là loại bỏ mọi sự phức tạp, mà là đặt sự phức tạp vào đúng vị trí của nó."
